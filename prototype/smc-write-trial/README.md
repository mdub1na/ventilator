# Ограниченная проба записи SMC

Отдельный инструмент M2-01 для точного сочетания `Mac15,7` + macOS 27.0. Он не входит в Ventilator.app и не изменяет read-only прототип `prototype/smc-read/`.

## Безопасные команды разработки

```bash
make build
make test
./smc-write-trial trial --dry-run
./smc-write-trial restore --dry-run
./smc-write-trial ftst-check --dry-run
./smc-write-trial ftst-minimum --dry-run
./smc-write-trial restore-unlock --dry-run
./smc-write-trial observe-baseline --read-only
```

Все команды `--dry-run` только читают SMC. `trial` и `ftst-check` собирают пять снимков за 10 секунд; `trial` печатает рассчитанные цели. `restore` и `restore-unlock` проверяют фиксированный план возврата. Они не требуют `sudo`.

`observe-baseline --read-only` делает 61 чтение за минуту и завершает работу при изменении `Ftst`, режимов или целей, ошибке чтения либо прерывании. Успешный интервал не доказывает безопасность новой записи или надёжное восстановление. Режим описан в [отдельном документе](../../docs/features/baseline-observer.md); на `Mac15,7`/macOS 27.0 он проверен без записи 2026-09-26. В песочнице Codex открытие AppleSMC может потребовать отдельного разрешения среды запуска.

Тесты `make test` также моделируют отложенное изменение после двух исходных снимков и отказ чтения/ожидания без обращения к SMC.

После любой попытки прямой записи `trial` в коде наблюдает 61 исходный снимок за минуту, включая случаи ошибочного ответа `F0Md`. Изменение внутри окна запускает повторное восстановление; если полный ручной режим так и не был виден, результат остаётся критически неподтверждённым. Симуляции охватывают изменение внутри и за пределами окна. `trial --apply` по-прежнему заблокирован.

`ftst-check` в коде теперь ждёт до 10 секунд появления записи `Ftst=1`; если её пока не видно, явно отправляет `Ftst=0` даже после ответа об ошибке на первую запись и наблюдает исходное состояние ещё минуту. Симуляции проверяют изменение как внутри, так и после этого окна. В последнем случае код сообщает о неподтверждённом эффекте с `CRITICAL` вместо «исходное состояние проверено». Ошибка компенсирующей записи не пропускает минутное наблюдение и также оставляет критический результат. Это не разрешает запуск `--apply` и не доказывает аппаратное восстановление.

## Команды с записью

`trial --apply`, `ftst-check --apply` и использованные `ftst-check --apply-reviewed`/`ftst-minimum --apply-reviewed` отвергаются **до открытия SMC**. Признак `VENTILATOR_MINIMUM_SUPERVISED=1` не открывает использованный допуск; обе supervised-оболочки не могут запустить новую запись актуальным бинарником. Следующая запись требует нового протокола, ревью и решения пользователя. Не запускайте старый бинарник с историческими командами; фактические результаты — в [журнале](../../docs/features/ftst-check-trial.md).

`ftst-supervised.sh` применялся для **одной ограниченной аппаратной пробы** 2026-09-27. Он выполнил два read-only preflight, интерактивное подтверждение, `Ftst: 0 → 1 → 0` и независимое минутное чтение после выхода процесса. Чтение обнаружило краткие режимы `[0,0]` после очистки `Ftst`, затем устойчивый возврат к `[3,3]` при нулевых целях. Финальная строка старого бинарника неверно утверждала, что режимы не менялись. Новый код относит такой результат к невыполненному критерию неизменности режимов при подтверждённом исходном состоянии. Повторный `--apply-reviewed` заблокирован до открытия SMC; дальнейшая запись требует нового ревью. [Полный протокол](../../docs/features/ftst-check-trial.md#420-повторная-ограниченная-проба-ftst-2026-09-27) не подтверждает ручной RPM или аварийный возврат из ненулевых целей.

`trial_rehearse_ftst_minimum_recovery` сначала добавлена как тестируемая state machine. Она моделирует одну запись `Ftst=1`, ограниченное чтение до появления минимальных ненулевых целей и возврат с обнулением перед `Ftst=0`. Тесты проверяют также отказ обнуления и недопустимую температуру. [Протокол §4.21](../../docs/features/ftst-check-trial.md#421-подготовка-пробы-восстановления-из-минимальных-целей--только-код) описывает этот изолированный этап.

`ftst-minimum --dry-run` только читает SMC. Для аппаратного запуска был подготовлен `ftst-minimum-supervised.sh`: интерактивный root Terminal, проверка свежести бинарника и SHA-256, два предварительных чтения, точная форма `ftst-minimum --apply-reviewed --confirm FTST-MINIMUM-Mac15,7-27.0` и независимое чтение после выхода CLI. При отрицательном результате он запускал `restore-unlock` и ещё один наблюдатель; неподтверждённый возврат требовал перезагрузки. Внутренний `alarm(180)` не гарантирует прерывания блокирующего IOKit или защиты от `SIGKILL`. Подготовка описана в [§4.22](../../docs/features/ftst-check-trial.md#422-ограниченный-cli-для-пробы-минимальных-целей--подготовка-без-записи); текущий бинарник возвращает код `2` на её пишущую форму до открытия SMC.

Журнал этого запуска получен 2026-09-29: приняты две записи `Ftst: 0 → 1 → 0`, ожидание прервано при GPU `−1,95 °C`. Минимальные цели `[1350,1458]` появились после команды очистки и затем обнулились без записи целей. Два независимых минутных окна подтвердили системное состояние. Финальная отрицательная оценка относится к неподтверждённому целевому порядку восстановления; журнал завершается подтверждённым возвратом. Ручные RPM и обнуление минимальных целей перед `Ftst=0` не испытаны. Точный результат — в [§4.24](../../docs/features/ftst-check-trial.md#424-проба-минимальных-целей--журнал-получен-2026-09-29).

Если после сборки изменился C/H исходник или `Makefile`, сценарий останавливается с кодом `2` **до открытия SMC** и просит выполнить `make -C prototype/smc-write-trial build`. Эта проверка времени файлов предотвращает случайный запуск явно устаревшего бинарника, но не заменяет сверку его SHA-256 с ревью. Повторять аппаратную пробу только ради прохождения температурного допуска не планируется.

Только для аварийного восстановления после отдельной оценки состояния остаются:

```bash
sudo ./smc-write-trial restore --apply --confirm RESTORE-Mac15,7-27.0
sudo ./smc-write-trial restore-unlock --apply --confirm RESTORE-UNLOCK-Mac15,7-27.0
```

Не запускайте команды восстановления как обычную проверку сборки. Первая `restore-unlock --apply` завершилась `CRITICAL`, потребовалась перезагрузка. Последующая проба §4.24 подтвердила системный возврат после перехода `Ftst` с минимальными целями, появившимися после очистки; возврат из ручного режима `1` остаётся непроверенным.

После первого критического случая CLI при `CRITICAL` сначала печатает срочное сообщение, затем сохранённые попытки записи (`key`, `ok`, `kernel`, `smc`) и результат отдельного чтения `post_failure`. Если чтение не удалось, в событии стоит `read_ok=false`. Повторная проба не вошла в ветку `CRITICAL`, поэтому её диагностический вывод при аппаратном отказе ещё не проверен.

Аварийный `restore-unlock` при `Ftst=1` переводит только ручные режимы `1` в `0`, затем допускает очистку `Ftst` при режимах `0`/`3` и минимальных целях. Подтверждение требует 61 последовательный исходный снимок с интервалом в секунду и может занять до 90 шагов наблюдения. После положительного результата нужен независимый read-only запуск из другого процесса. В §4.24 минимальные цели наблюдались уже при `Ftst=0` и вернулись к нулю без записей целей. Обнуление минимальных целей **до** очистки `Ftst` аппаратно не проверено; при неподтверждённом возврате требуется read-only проверка и, если исходный режим не восстановлен, перезагрузка.

Если через десять шагов после очистки `Ftst` оба вентилятора по-прежнему в режиме `0`, код один раз повторяет освобождение и обнуление целей, затем продолжает проверку исходного состояния. Для смешанного состояния `0`/`3` эта ветка ничего не пишет. Подставные тесты подтверждают порядок и критический результат, когда цели остаются ненулевыми; на SMC эта ветка не запускалась. Время ожидания может превысить 90 секунд на длительность этой попытки.

Перед аппаратной пробой после слияния зафиксируйте точный исходник и бинарник в журнале:

```bash
git rev-parse HEAD
shasum -a 256 prototype/smc-write-trial/smc-write-trial
```

`trial` проверял только прямой переход `F0Md`/`F1Md` в ручной режим и **никогда не записывал `Ftst`**. Прямая проба 2026-09-25 получила `smc=0x82` при записи `F0Md`; переход в ручной режим не был подтверждён. Отдельная `ftst-check --apply` записала `Ftst=1` с ответом SMC `0`, но независимое чтение позже обнаружило `Ftst=1`, изменённые режимы и цели. `restore-unlock` не подтвердил восстановление; после перезагрузки исходное состояние вернулось. Ни одна команда не пишет `FS! `.

Протокол короткой пробы и её ограничения — в [`docs/features/ftst-check-trial.md`](../../docs/features/ftst-check-trial.md).
