# Участие в разработке Ventilator

Спасибо за интерес к проекту. Сейчас это прототип мониторинга **только для чтения** на `Mac15,7`; работа приложения и управление вентиляторами на других моделях ещё не подтверждены. Перед изменениями прочитайте [исследование](docs/research/research-architecture.md) и [план](BACKLOG.md): там разделены проверенные факты, решения и гипотезы.

## Предложение изменений

1. Выберите один пункт из `BACKLOG.md` или опишите конкретную ошибку. Для крупной новой функции сначала обсудите её в GitHub issue, чтобы согласовать проверяемый результат.
2. Создайте ветку от актуального `main`. Один pull request должен решать одну задачу. Используйте понятное имя ветки, например `feat/menu-bar-window` или `fix/sensor-unavailable`.
3. Обновите код и относящуюся к нему документацию в одном PR. Не выдавайте целевое поведение за уже проверенное. Для нового датчика укажите сырой SMC-ключ, источник значения и модель/версию macOS, на которой проверена подпись.
4. В описании PR укажите задачу, изменения, команды проверки и их результат. Для изменений интерфейса приложите снимок экрана; для аппаратных наблюдений укажите модель Mac и версию macOS. Отметьте, что не удалось проверить.
5. Дождитесь зелёной проверки GitHub Actions и ревью сопровождающего перед слиянием. Обычные изменения в `main` вносятся через PR.

Коммиты называйте на английском в формате Conventional Commits: `feat:`, `fix:`, `docs:`, `test:`, `refactor:` или `chore:`. Например: `fix(menu-bar): show unavailable CPU temperature`.

## Локальные проверки

Для проверки документации нужен Python 3 и зависимости из `requirements-docs.txt`:

```bash
python3 -m venv .venv
. .venv/bin/activate
python3 -m pip install -r requirements-docs.txt
make check
```

Если меняли нативные прототипы, соберите их на macOS:

```bash
make -C prototype/smc-read build
make -C prototype/menu-bar build
make -C prototype/login-item build
make -C prototype/smc-write-trial clean build test
make -C prototype/helper-ipc smoke
make -C prototype/helper-ipc package-smoke
make -C prototype/helper-ipc control-lease-test
make -C prototype/helper-ipc control-intent-test
```

Сборка и тесты `smc-write-trial` не требуют записи в SMC. Не запускайте его команды `--apply` как обычную проверку PR. Новые аппаратные пробы заблокированы после [случая с `Ftst`](docs/features/ftst-check-trial.md); прямая проба и её исходный допуск записаны в [отдельном протоколе](docs/features/manual-fan-control-trial.md). Команды восстановления остаются аварийными и не входят в тесты.

Если меняли Kotlin-модель, запустите `gradle test` из `prototype/kotlin-read/`; если меняли окно, выполните `gradle :test` из `prototype/desktop-app/` с JDK 25 и совместимой версией Gradle. Для проверки локального `.app` есть `gradle createDistributable -Pcompose.desktop.packaging.checkJdkVendor=false` (на Homebrew JDK). В репозитории пока нет Gradle Wrapper; укажите в PR использованные версии. Не утверждайте, что проверили macOS UI, если только собрали код: при возможности проверьте поведение на реальном Mac.

Если меняли Kotlin/Native IOKit пробу, выполните `gradle linkDebugExecutableMacosArm64` из `prototype/kotlin-native-iokit/` на Apple Silicon Mac. Для подтверждения доступа к AppleSMC запустите собранный `iokit-smoke.kexe` вне песочницы и укажите результат в PR.

GitHub Actions запускает проверку документации, изолированные тесты `smc-write-trial` и контракта `helper-ipc` на macOS. Подписанные XPC и аппаратные сценарии в workflow не выполняются, поэтому их результат надо записывать в PR.

`prototype/helper-ipc` запускает лишь временные пользовательские XPC-службы из ad hoc подписанных копий. Проба требует доступа к пользовательскому `launchctl`, не обращается к SMC, проверяет двусторонний отказ по несовпадающему `cdhash` и удаление обеих служб. При сообщении `CRITICAL` проверьте напечатанное имя службы и сохранённый plist до повторного запуска. Эта проба не подтверждает доверенную подпись будущего привилегированного helper.

`package-smoke` отдельно создаёт временный тестовый `.app`, регистрирует и отменяет пользовательский LaunchAgent через `SMAppService.agent`. При ошибке он сохраняет пакет для проверки; пока `unregister` и отсутствие службы не подтверждены, не удаляйте его вручную. Этот тест не меняет `Ventilator.app` и не регистрирует LaunchDaemon.

`daemon-prepare` создаёт отдельный read-only `.app` и подписывает его локальным действующим Apple Development сертификатом. Системная проба выполняется только явными командами `daemon-probe.sh register/status/check/unregister/cleanup` из [инструкции прототипа](prototype/helper-ipc/README.md). Для запуска macOS может потребовать разрешение фонового объекта. Перед удалением пакета обязательны `notRegistered` и отсутствие службы в системном `launchctl`. Этот тест не пишет в SMC и не меняет основной `Ventilator.app`.

`integrated-probe.sh prepare` создаёт временную подписанную копию настоящего Compose `Ventilator.app` с read-only daemon и JNI-мостом. Регистрация, XPC запрос из главного процесса, отмена регистрации и удаление пакета — отдельные явные команды. Не удаляйте временный пакет при `requiresApproval` или `enabled`; сначала выполните `unregister` и проверьте отсутствие системной службы. Обычный запуск UI не включает этот daemon.

## Безопасность аппаратных проверок и данных

- Не добавляйте запись в SMC или команды изменения оборотов в текущие read-only прототипы. Исследование управления выделено в этап M2 плана; ему нужны отдельная реализация и проверка восстановления системного режима после ошибки, выхода и сна.
- Не принимайте показания одного SMC-ключа или одной модели за универсальные. При недоступном чтении показывайте неизвестное состояние, не подставляйте ноль или другой датчик молча.
- Не добавляйте в репозиторий ключи доступа, серийные номера, UUID устройств, персональные пути, сырые диагностические дампы и сведения о частной инфраструктуре. Перед публикацией снимков экрана и логов удалите такие данные.
- В PR с проверкой на оборудовании запишите точные шаги, наблюдённый результат и ограничения. Аппаратное испытание без воспроизводимого описания не закрывает пункт плана.

`AGENTS.md` содержит дополнительные указания для работающих с репозиторием агентов; этот документ задаёт общий процесс для участников GitHub.
