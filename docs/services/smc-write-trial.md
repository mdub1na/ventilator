# Ограниченный инструмент первой записи SMC

## 1. Responsibility

Одноразовый CLI для этапа M2-01 проверяет точное сочетание `Mac15,7` + macOS 27.0. Прямая команда строит цель выше текущего охлаждения для двух вентиляторов и выполняет пару «ручной режим → цель» с возвратом системного режима `3`. Отдельная короткая команда `ftst-check` проверяет только `Ftst: 0 → 1 → 0`; `restore` и `restore-unlock` доступны второму Terminal независимо от процесса пробы.

Инструмент не входит в Ventilator.app, не является привилегированным helper и не принимает произвольные ключи, типы, байты или RPM. Прямая команда не записывает `Ftst`; короткая команда не записывает положительные цели RPM. `FS! ` не записывается никогда. Прямая аппаратная проба 2026-09-25 дошла до `F0Md`, которую SMC отклонил `0x82`. Первая запись `Ftst=1` вызвала критический случай с отложенным изменением и неподтверждённым восстановлением. Повторная ограниченная проба 2026-09-27 подтвердила возврат после краткого режима `[0,0]` с нулевыми целями. Все формы аппаратных проб, включая израсходованную `--apply-reviewed`, теперь заблокированы до открытия SMC. Команды восстановления доступны.

## 2. Local contract

HTTP API нет. CLI распознаёт десять точных форм; формы `trial --apply` и `ftst-check --apply` завершаются отказом до открытия SMC:

```text
smc-write-trial trial --dry-run
smc-write-trial restore --dry-run
smc-write-trial ftst-check --dry-run
smc-write-trial restore-unlock --dry-run
smc-write-trial observe-baseline --read-only
smc-write-trial trial --apply --confirm TRIAL-Mac15,7-27.0
smc-write-trial restore --apply --confirm RESTORE-Mac15,7-27.0
smc-write-trial ftst-check --apply --confirm FTST-CHECK-Mac15,7-27.0
smc-write-trial ftst-check --apply-reviewed --confirm FTST-REVIEWED-Mac15,7-27.0
smc-write-trial restore-unlock --apply --confirm RESTORE-UNLOCK-Mac15,7-27.0
```

Доступные команды восстановления `--apply` требуют root. Процедуры `trial --apply`, `ftst-check --apply` и `ftst-check --apply-reviewed` сохраняются в коде для анализа, но все заблокированы до открытия SMC. Исторический сценарий `ftst-supervised.sh` выполнял два read-only preflight, один подтверждённый запуск и независимый минутный наблюдатель; изменённое либо нечитаемое состояние вызывало `restore-unlock` и повторное наблюдение. Его пишущая команда теперь отклоняется до SMC. Неизвестный аргумент прекращает процесс до открытия пути записи.

Перед первым read-only вызовом сценарий проверяет, что бинарник не старее `Makefile` и всех C/H файлов из цели `smc-write-trial` в локальном `Makefile`. Отсутствующий или более новый исходник даёт код `2` без обращения к SMC и указание пересобрать программу. Метки времени не доказывают идентичность исходников и бинарника: точный SHA-256 остаётся отдельной частью аппаратного протокола.

Для `--apply-reviewed` код выхода `2` теперь означает постоянный отказ **до открытия SMC**. В исторической пробе этот же код означал отказ до первой записи из-за среды, preflight, отсутствия root/TTY или подтверждения либо финального чтения. Подставной тест сценария по-прежнему проверяет маршрутизацию при кодах `2` и `1`, но не разрешает новое аппаратное испытание.

## 3. How it is built

`make build` собирает отдельный macOS binary. В live transport команда записи AppleSMC `6` доступна только закрытым функциям для найденных `F0Md`/`F1Md`, `F0Tg`/`F1Tg` и точного `Ftst`. Перед каждой записью повторно проверяются type/size. State machine допускает для `Ftst` только байты `0`/`1`; операция `ftst-check` не пишет цели при штатном ходе, а операция `trial` не пишет `Ftst`. Операции для `FS! ` или произвольного ключа нет.

Прямой переход каждого вентилятора записывает цель не позднее 250 мс после принятой команды ручного режима. Через пять секунд фактические RPM должны вырасти и попасть в допуск. При изменившемся или неизвестном состоянии state machine записывает Auto и нулевую цель обоим вентиляторам, затем до пяти секунд ждёт фактические режимы `[3, 3]`, `Ftst = 0` и нулевые цели.

После первой аппаратной пробы cleanup сначала читает оба режима и цели. Если SMC отклонил переход и исходные `[3, 3]`, `Ftst = 0`, цели `0` сохранились, команда завершает отказ без дополнительных записей. Если состояние менялось или чтение не удалось, выполняется прежняя процедура восстановления. Подтверждение безопасного состояния требует также нулевых целей, поэтому сообщение CLI больше не называет нетронутый режим «восстановленным».

Для `ftst-check` была предусмотрена отдельная state machine из [протокола](../features/ftst-check-trial.md): после чтения `Ftst=1` команда без выдержки записывает `0`. В первой пробе непосредственное чтение показало `Ftst=0`, поэтому явная очистка не выполнялась; позже независимо обнаружены `Ftst=1`, изменённые режимы и цели. Первая `restore-unlock` требовала обнулить цели **до** очистки `Ftst` и не подтвердила возврат. Пересмотренная аварийная команда сначала проверяет, что оба режима вышли из ручного `1`, затем очищает `Ftst` при режимах `0`/`3` без требования нулевых целей и требует 61 последовательный исходный снимок за время до 90 шагов наблюдения. Это unit-тестированный план, а не проверенное аппаратное восстановление. При `CRITICAL` CLI выводит предупреждение, буфер попыток записи с кодами IOKit/SMC и `post_failure` readback либо ошибку чтения.

После подтверждённой очистки `Ftst` и десяти шагов без системного возврата команда делает одну дополнительную попытку режима `0` и нулевой цели **только когда оба режима остаются `0`**. При режиме `3` хотя бы одного вентилятора его возможная системная цель не переписывается. Попытка может прибавить до пяти секунд к общему ожиданию; успех по-прежнему требует полной минуты последующих исходных снимков, а не только ответа на запись. Это проверено подставными состояниями с успешным и отвергнутым обнулением, но не изменённым SMC.

Если `Ftst=1` принят транспортом, но немедленное чтение не показывает `1`, пересмотренная state machine продолжает читать до 10 секунд. При видимом изменении она запускает восстановление; при отсутствии изменения явно пишет `Ftst=0` и наблюдает ещё минуту. Если эффект проявляется в этом окне, запускается повторное восстановление; если не проявляется, итог всё равно `TRIAL_RUN_WRITE_EFFECT_UNVERIFIED`, а не подтверждённый возврат. CLI выводит `CRITICAL` и отдельный readback. Симуляция эффекта после окончания окна сохраняет этот статус; блокировка `--apply` остаётся.

## 5. Local verification

На `Mac15,7`, macOS 27.0, 2026-09-23:

- `make clean build test` собрал transport и выполнил тесты pure logic/state machine;
- `restore --dry-run` прочитал режимы `[3, 3]`, `Ftst = 0`, два `flt `/4 target key и вывел фиксированный план;
- `trial --dry-run` сделал пять снимков за 10 секунд и вычислил цели 1650/1758 RPM из свежих `Ac = 0`, `Mn = 1350/1458`;
- на эту дату ни одна команда `--apply`, selector `6` или запись SMC не запускалась.

Первая `trial --apply` 2026-09-25, commit `82ea370` и SHA-256 `b24bec38e7ac8d1f830e23b4ed66ee47aab8e5eaa975e1b353ee358ba09d0aa8`, прошла preflight, но SMC вернул `0x82` на `F0Md`. Положительные цели RPM не записывались. Независимое чтение после завершения показало `[3, 3]`, `Ftst = 0`, цели `[0, 0]`; фактическое восстановление из ручного режима не испытано. Подробные значения и ограничения приведены в [протоколе](../features/manual-fan-control-trial.md#51-результат-первой-прямой-пробы-2026-09-25).

После добавления короткой пробы unit-тесты прошли; `restore-unlock --dry-run` подтвердил исходное состояние. Первая `ftst-check --apply` 2026-09-25, commit `20baa0c685dfaf2d2c6674f2e33e5151a0999b0e`, SHA-256 `e2330442bef7b111ece2486b19fc9954742ea0fdb11b800d154c5ec99844687d`, получила `kernel=0`, `smc=0` на записи `Ftst=1`, но непосредственное чтение показало `Ftst=0`. После выхода независимое чтение обнаружило `Ftst=1`, режимы `[0, 0]` и цели `[1350, 1458]`. `restore-unlock --apply` не подтвердил возврат; перезагрузка восстановила исходные `[3, 3]`, `Ftst=0`, цели `[0, 0]`, подтверждённые двумя чтениями. Подробности и неизвестные причины — в [журнале пробы](../features/ftst-check-trial.md#41-первая-запись-ftst-2026-09-25).

После инцидента добавлена диагностика критических отказов и unit-тест, в котором минимальные цели не удаётся обнулить. Он демонстрирует возможную ветку кода, а не установленную причину аппаратного отказа. Сборка и тесты не выполняют записей SMC; новый вывод восстановления на устройстве не испытывался.

Независимый [наблюдатель исходного состояния](../features/baseline-observer.md) 2026-09-26 без root прочитал 61 снимок за минуту на `Mac15,7`/macOS 27.0. Все показали `Ftst=0`, режимы `[3,3]`, цели `[0,0]`; итог `complete/stable`, код 0. Это проверка команды чтения в покое, не проверка задержки после новой записи.

Цикл наблюдения затем вынесен в read-only state machine. Unit-тест моделирует два исходных снимка и изменённый третий, а также ошибку чтения, прерывание и ошибку ожидания. После этого реальная команда повторно прочитала 61 исходный снимок за 60,46 секунды на той же модели и версии ОС. Отложенное изменение SMC аппаратно повторно не проверялось.

Дополнительные unit-тесты моделируют принятую запись `Ftst=1`, которая становится видимой через секунду, после явного `Ftst=0` либо уже после минутного окна; проверяют также рост температуры сразу после записи. Буфер журнала теперь хранит все чтения в порядке монотонного времени и ставит JSON `null` для нечитанных RPM/температур. `make build test` проходит без аппаратной записи. Это подготовка протокола, а не доказательство возврата в системный режим.

Пересмотр `restore-unlock` проверен тестами на прежнем изменённом снимке с минимальными целями, задержанном применении `Ftst=0`, отсутствии возврата системы и повторном включении `Ftst`. На `Mac15,7`/macOS 27.0 новый `restore-unlock --dry-run` прочитал `Ftst=0`, режимы `[3,3]`, цели `[0,0]`; selector записи не применялся. Положительный результат будущей аварийной команды должен быть независимо перепроверен после завершения процесса.

Аудит 2026-09-27 закрыл ранний путь успеха самостоятельной `restore-unlock` после одного исходного снимка: теперь он требует непрерывные 60 секунд наблюдения и при позднем изменении пытается восстановить состояние, сохраняя `CRITICAL`. Ветка `Ftst=0` после очистки режимов и целей также наблюдает полную минуту. Самостоятельная `restore --apply` перед сообщением об успехе запускает `observe-baseline`; изменение или ошибка чтения возвращают `CRITICAL`. Это проверено C unit-тестами и сборкой на `Mac15,7`/macOS 27.0 **без записи в SMC**. Аппаратное восстановление из изменённого состояния остаётся неподтверждённым.

Ограниченный запуск `ftst-supervised.sh` 2026-09-27 на `Mac15,7`/macOS 27.0 с SHA-256 бинарника `f2b49ebd1b6a8aef71bff0827d96072c437d8155a0b36e0a201b3820bc8dee9b` получил `kernel=smc=0` на `Ftst=1` и `Ftst=0`. Запись `1` стала видимой примерно через секунду; после очистки режимы кратко были `[0,0]` с нулевыми целями, затем вернулись к `[3,3]`. Внутреннее и два независимых минутных наблюдения подтвердили исходное состояние. Полный [протокол §4.20](../features/ftst-check-trial.md#420-повторная-ограниченная-проба-ftst-2026-09-27) фиксирует неисполненный критерий неизменности режимов и непроверенные ручные RPM/аварийный возврат. В коде статус такого хода теперь отрицательный при подтверждённом исходном состоянии; `--apply-reviewed` заблокирован до открытия SMC. Проверка этого изменения — unit-тест, без ещё одной аппаратной записи.

Следующая `trial_rehearse_ftst_minimum_recovery` в `trial_actions.c` проверена только подставными backend: ожидаемая последовательность обнуляет появившиеся минимальные цели перед `Ftst=0`, а отвергнутые нули без возврата системы дают критический результат. Она не имеет CLI вызова и не связана с daemon. Аппаратный результат и независимое наблюдение после процесса для этой новой последовательности ещё отсутствуют.

## 6. Local setup

```bash
make -C prototype/smc-write-trial clean build test
prototype/smc-write-trial/smc-write-trial restore --dry-run
prototype/smc-write-trial/smc-write-trial trial --dry-run
prototype/smc-write-trial/smc-write-trial restore-unlock --dry-run
prototype/smc-write-trial/smc-write-trial ftst-check --dry-run
prototype/smc-write-trial/smc-write-trial observe-baseline --read-only
```

Команды `--apply` и `--apply-reviewed` не относятся к проверке сборки и заблокированы до открытия SMC. Аварийные команды восстановления оставлены доступными. Исходный порядок допуска описан в [прямом протоколе](../features/manual-fan-control-trial.md) и [протоколе `Ftst`](../features/ftst-check-trial.md).

## 7. Limits

Обработчики `SIGINT`/`SIGTERM`/`SIGQUIT` направляют контролируемое завершение в восстановление, но процесс не может защититься от `SIGKILL`, аварии ядра или потери питания. Теперь аппаратная проба показала ещё один предел: чтение сразу после записи не гарантирует устойчивого исходного состояния, а независимая команда не смогла подтвердить восстановление. Сон, crash, отложенные изменения и внешний watchdog относятся к пересмотру M2-02. Проверка `Ftst` не подтвердила ручное управление RPM. Причины `0x82` и отложенного изменения на этой машине не установлены.
