# Возможно ли управление вентиляторами Mac на Kotlin?

**Вывод исследования:** да, приложение для macOS можно построить преимущественно на Kotlin. Compose Multiplatform Desktop подходит для интерфейса, Kotlin/JVM — для логики приложения, Kotlin/Native может обращаться к C API IOKit. На 22 сентября 2026 года в репозитории есть работающий прототип **только для чтения** на `Mac15,7`. Ручное управление **не подтверждено**.

Документ отделяет внешние проверенные факты от решений и гипотез. Проверка конкретной модели означает аппаратный опыт; публикация другого приложения не доказывает работоспособность нашего.

### 1.1. Измерения на `Mac15,7` с macOS 27.0

Команда `make build` в `prototype/smc-read/`, затем запуск утилиты smc-read с обычным и полным выводом в пользовательском процессе 2026-09-22. Внутри песочницы Codex `IOServiceOpen` вернул `kIOReturnNotPermitted`; запуск вне неё без `sudo` прошёл. Числа температур — снимок состояния, не постоянные характеристики модели.

| Наблюдение | Результат | Что это позволяет утверждать |
|---|---|---|
| Число вентиляторов | `FNum = 2` | Две отдельные строки мониторинга в UI. Положение «левый/правый» не подтверждено; `F0ID`/`F1ID` не дали подписи. |
| Вентилятор 0 | `F0Ac = 0`, `F0Tg = 0`, `F0Mn = 1350`, `F0Mx = 5349` RPM; `F0Md = 3` | Фактические, целевые и граничные значения читаются. Нулевые обороты при системном режиме не надо трактовать как поломку из-за ненулевого `Mn`. |
| Вентилятор 1 | `F1Ac = 0`, `F1Tg = 0`, `F1Mn = 1458`, `F1Mx = 5777` RPM; `F1Md = 3` | Возможен отдельный мониторинг двух вентиляторов; отдельное управление остаётся гипотезой. |
| Дополнительные ключи | `Ftst = 0`; `FS! ` не прочитан | Режим `3` в открытых реализациях называют System. Наличие `Ftst` не доказывает доступ к записи или необходимость его менять. |
| Температура | Из 2305 ключей SMC — 252 с префиксом `T`, все читаются; 215 значений типа `flt ` попали в фильтр 10–115 °C. Примеры: `TAOL ≈ 30.6`, `TB0T ≈ 34`, `TCMb ≈ 56.6`, `TCMz ≈ 55.1` °C. При повторном чтении `TCMz` изменился до ≈ 64.2 °C. | Мониторинг изменяющихся температурных значений подтверждён. Число 215 не означает 215 независимых компонентов: возможны агрегаты, дубли и ошибочные совпадения фильтра. |

**Проверка нулевых RPM, 2026-09-22.** Начальный прямой снимок выше содержал `F0Ac = F1Ac = 0` вместе с `F0Tg = F1Tg = 0`. После пользовательского снимка с двумя нулями отдельные прямые запуски `prototype/smc-read/smc-read` показали вращение: примерно 1350 и 1460 RPM, системные цели 1350 и 1458 RPM. Меню в старом AppKit прототипе могло показывать устаревший снимок, так как `Timer.scheduledTimer` ставил опрос в default run-loop mode; [Apple описывает](https://developer.apple.com/documentation/foundation/runloop/run_loop_modes) отдельный режим отслеживания событий и common modes. Таймер переведён в common modes и чтение запрашивается при открытии меню (`prototype/menu-bar/StatusItem.swift`). Нельзя по одному пользовательскому снимку установить, были ли тогда фактически остановлены оба вентилятора; обновление видимого меню после исправления ещё проверять на устройстве.

При проверке M1-01 новый Kotlin/JVM путь через `smc-read --status-json` снова зафиксировал оба `Ac = 0 RPM` при `TCMz = 75,34 °C`. Следующее отдельное прямое чтение `prototype/smc-read/smc-read` подтвердило `F0Ac = F1Ac = F0Tg = F1Tg = 0`, `F0Md = F1Md = 3` и `TCMz = 61,55 °C`. Это подтверждает, что ноль в **этом** интервале был самим показанием SMC с нулевыми целями; момент пользовательского снимка и физическое вращение независимо не измерялись. Температура `TCMz` быстро меняется и не задаёт один универсальный порог включения вентиляторов.

**Повторная проверка CPU, 2026-09-22.** Скрипт `prototype/smc-read/thermal-study.py` сделал 3 снимка в покое, 8 за 30 секунд вычислительной нагрузки на 4 процесса и 3 при остывании; каждый раз прочитаны 215 правдоподобных температур. Только команды чтения SMC. Среднее трёх исходных значений `TCMz` — ≈59,3 °C, пик за время нагрузки — 90,7 °C, первое измерение после неё — 92,0 °C, последнее — 65,7 °C. `TCMb`: ≈57,0 → 87,0 → 89,6 → 65,3 °C. Контрольные `TAOL` держался около 32,4 °C, `TB0T` около 35,4–35,5 °C, `TH0a` около 34,0 °C. Обороты обоих вентиляторов оставались приблизительно на 1340–1490 RPM; этот краткий опыт не проверяет политику их разгона. Сырые 14 снимков сохранены локально в `/private/tmp/ventilator-thermal-study.jsonl` и не входят в репозиторий.

**Выбор для строки меню на этой машине:** `TCMz` как «температура CPU, максимум кристалла» (`CPU die max / hotspot`). Название согласуется с независимыми каталогами [iSMC](https://github.com/dkorunic/iSMC/blob/master/smc/sensors.go) и [OSHI SmcUtil](https://www.oshi.ooo/xref/oshi/util/platform/mac/SmcUtil.html), где `TCMb` указан как среднее, `TCMz` — как максимум. Реакция `TCMz` при нагрузке именно CPU наблюдалась на нашем `Mac15,7`; это достаточное основание для **рабочей** подписи в UI этой модели, но не официальная документация Apple и не доказательство идентичной семантики на других моделях. Сырой ключ показан в карточке. Если ключ недоступен или значение неправдоподобно, температура в значке неизвестна; не подменять её `TCMb` молча.

**Имена компонентов.** Открытые каталоги связывают `TAOL` с окружающей средой, `TB0T` с батареей, `TCMb`/`TCMz` с зоной CPU, а семейства `Tp`/`Te`/`Tg` — с ядрами CPU и GPU: [iSMC](https://github.com/dkorunic/iSMC/blob/master/smc/sensors.go), [MacMonitor](https://github.com/ryyansafar/MacMonitor/blob/main/SENSORS.md), [smcprobe](https://github.com/ianm199/smcprobe). Сопоставление `TCMz` для CPU подкреплено наблюдением выше. Для GPU проведена отдельная проверка `Tg0D` ниже; остальные имена на `Mac15,7` остаются гипотезами. Разные каталоги по-разному называют `TRDX`, поэтому этот код не используется как GPU.

|---|---|---|
| Окружающая среда | `TAOL` | [iSMC](https://github.com/dkorunic/iSMC/blob/master/smc/sensors.go) |
| Аккумулятор | `TB0T`, `TB1T`, `TB2T` | [MacMonitor на M2](https://github.com/ryyansafar/MacMonitor/blob/main/SENSORS.md) |
| CPU / SoC | `TCMz` — выбранный максимум CPU die; `TCMb` — наблюдаемый агрегат, `Tp*`/`Te*` — кандидаты на отдельные ядра | [iSMC](https://github.com/dkorunic/iSMC/blob/master/smc/sensors.go), [OSHI](https://www.oshi.ooo/xref/oshi/util/platform/mac/SmcUtil.html), локальная корреляция выше; [smcprobe на M3 Max](https://github.com/ianm199/smcprobe) для семейств ядер |
| GPU | `Tg0D` и другие `Tg*` | [smcprobe на M3 Max](https://github.com/ianm199/smcprobe); собственная нагрузка GPU ниже |
| Накопитель | `TH0a`, `TH0b`, `TH0x` | [smcprobe на M3 Max](https://github.com/ianm199/smcprobe); собственная нагрузка внутреннего накопителя ниже |

**Проверка GPU на `Mac15,7`, 2026-09-22.** Небольшой Metal compute workload работал 22 секунды; `smc-read --temperatures-json` снимал короткую серию до, во время и после нагрузки. `Tg0D` вырос с 44,51 до 67,64 °C и в первом снимке после нагрузки снизился до 55,53 °C. Соседние `Tg1B`/`Tg05` двигались сходно; контрольный `TH0a` оставался около 32,0–32,3 °C, `TAOL` — около 28,4 °C. Это подтверждает рабочую подпись **датчик GPU** для `Tg0D` на этой модели. Снимки и код разовой пробы лежали в `/private/tmp/ventilator-gpu-*`, не в репозитории.

**Проверка SSD на `Mac15,7`, 2026-09-22.** Скрипт `prototype/smc-read/storage-study.py` сделал 3 снимка в покое, 12 во время 45-секундной нагрузки и 4 после неё. Нагрузка записала не более 4 GiB во временный файл размером 512 MiB, затем читала его без файлового кеша; SMC использовался только для чтения. Среднее исходное значение `TH0a` было 29,41 °C, пик — 39,58 °C, последнее восстановительное значение — 36,86 °C. `TH0b`: 29,24 → 38,67 → 36,62 °C; `TH0x` повторил `TH0a`. Контрольные `TAOL` и `TB0T` изменились лишь на 0,06 и 0,20 °C. За опыт записано 4 GiB и прочитано 115,36 GiB; временный файл удалён. Это подтверждает рабочую подпись **температурная зона SSD** для `TH0a` на этой модели, согласованную с [картой `TH0*` для M3 Max](https://github.com/ianm199/smcprobe). Опыт не различает контроллер, NAND и другие подкомпоненты накопителя. Сырые 19 снимков сохранены локально в `/private/tmp/ventilator-storage-study.jsonl` и не входят в репозиторий.

Кроме рабочих выборов `TCMz`, `Tg0D` и `TH0a`, названия в левом столбце **не являются проверенной картой нашей модели**. Измерение каждого ключа происходит в разное мгновение, поэтому даже «max» и «average» из внешних каталогов нельзя проверять сравнением одного снимка.

### Источники низкоуровневого поведения, требующие собственной проверки

[Открытый проект macfan](https://github.com/raminsharifi/MacFanControl) сообщает о работе через `AppleSMC`, ключах RPM и ручном режиме на `Mac15,7`. В его [`fan.rs`](https://github.com/raminsharifi/MacFanControl/blob/main/src/fan.rs) ключ режима ищется как `F{n}md`/`F{n}Md`, а RPM кодируется по фактически прочитанному типу `flt ` или `fpe2`; [`smc.rs`](https://github.com/raminsharifi/MacFanControl/blob/main/src/smc.rs) проверяет размер перед командой записи; [`control.rs`](https://github.com/raminsharifi/MacFanControl/blob/main/src/control.rs) сначала включает ручной режим, при отказе ограниченно использует `Ftst`, а при восстановлении обрабатывает все затронутые вентиляторы до очистки `Ftst`. [README проекта](https://github.com/raminsharifi/MacFanControl/blob/main/README.md) прямо отделяет cleanup обычного выхода от случаев `SIGKILL` и потери питания, где нужен внешний способ восстановления. Это свидетельство разработчика сторонней программы, **не** документация Apple и **не** результат нашего прототипа на macOS 27. Пример [Stats](https://github.com/exelban/stats/blob/master/SMC/Helper/main.swift) подтверждает существование схемы с helper, но его README помечает fan control как «not maintained». Конкретные имена ключей, кодировки значений и переключение режима проверять на устройстве, а не копировать как гарантированный контракт.

## 2. Решения на текущем этапе

| Решение | Причина и отклонённая альтернатива | Цена / проверка |
|---|---|---|
| **D1. Пока работаем только с `Mac15,7` на macOS 27.0.** | Эта модель доступна для повторяемых аппаратных проверок. Mac mini, Intel/T2 и другие Apple Silicon — отдельная фаза. | Результаты нельзя переносить на другие модели или версии macOS. Очередность — в [плане](../../BACKLOG.md). |
| **D2. Интерфейс на Kotlin/JVM + Compose Desktop; доменная логика на Kotlin.** | Это документированный настольный путь Compose. KMP модуль с `commonMain` имеет смысл, если логика понадобится на нескольких платформах; при одной macOS цели он не обязателен. Альтернатива «Compose Desktop на Kotlin/Native без JVM» не соответствует текущей документации. | Нужно проверить интеграцию строки меню, жизненный цикл и размер пакета на реальном прототипе (M1/M3). |
| **D3. Для первой версии чтение: Kotlin/JVM → отдельная C-утилита; Swift/AppKit — для строки меню.** | Уже проверен полный путь от JVM до снимка датчиков и отдельно показан значок AppKit. Kotlin/Native открыл IOKit, но не читает SMC-ключи; при Compose Desktop на JVM он всё равно потребовал бы границы JNI или процесса. Прямой Swift-доступ к SMC также означал бы вторую реализацию протокола без выигрыша для текущего чтения. Альтернатива «всё JVM приложение от root» увеличила бы область привилегий. | Локальный `.app` с C reader и дочерним Swift значком собран и запущен. Kotlin остаётся единственным источником короткого снимка и уровня; пункты меню, скрытие окна и завершение проверены на устройстве (M1-03). Язык будущего привилегированного помощника выбирается отдельно в M2. |
| **D4. Чтение до записи; управление системой — начальное и аварийное состояние.** | Управление охлаждением может быть опасным при ошибке протокола или потере процесса. [Протокол первой пробы](../features/manual-fan-control-trial.md) допускает только точный `Mac15,7` + macOS 27.0, два вентилятора вместе и цель на 300 RPM выше свежего `max(Ac, Mn)`; произвольных ключей и снижения охлаждения нет. На этой машине сейчас прочитан режим `3`; нельзя считать, что простая запись режима `0` уже означает полное восстановление. | Перед первой записью нужны отдельный инструмент, заранее подготовленная независимая команда восстановления и явное аппаратное испытание. Watchdog/восстановление при crash, сне и удалении программы остаются M2-02, а не существующей защитой. |
| **D5. Первый выпуск — вне Mac App Store.** | Ограничение App Sandbox и практика Macs Fan Control делают Store зависимым от дополнительного доказательства. | Developer ID, нотарификация и обновление helper входят в M3. |
| **D6. Один элемент строки меню служит значком приложения и живым индикатором.** | Пользователь хочет видеть общую шкалу вентиляторов и температуру CPU без постоянно открытого окна; обычный щелчок переключает окно, контекстный щелчок открывает меню. Для простого значка подходит Compose `Tray`; составной прототип сделан на `NSStatusItem`. | Тёмная и светлая темы, оба щелчка, связь с Compose окном и читаемость при ограниченном месте проверены в локальном `.app`. |
| **D7. Автозапуск — настройка запуска при входе пользователя.** | `SMAppService.mainAppService` соответствует пользовательскому сценарию; запуск до входа не нужен для окна мониторинга. [Признак login launch](https://developer.apple.com/documentation/coreservices/keyaelaunchedasloginitem) позволяет скрыть окно именно при автоматическом старте. | В локальном `.app` проверены переключатель, статусы разрешения, запуск при следующем входе со скрытым окном, отсутствие запуска после выключения и оба входа на экран настроек. |

### Результат M0-03: границы процессов

| Вариант | Что проверено | Решение для первой версии |
|---|---|---|
| Kotlin/JVM → C по `ProcessBuilder`/JSON | `gradle --offline run --args=../smc-read/smc-read` повторно прочитал `TCMz`, RPM и уровни обоих вентиляторов 2026-09-22; таймаут и проверка схемы уже есть в Kotlin-прототипе. | **Выбран для чтения.** Оставить C-часть без записи; ограничить путь к упакованной утилите, размер вывода и ошибки при интеграции. |
| Kotlin/Native → `platform.IOKit` | `gradle --offline linkDebugExecutableMacosArm64` собрал [пробу](../../prototype/kotlin-native-iokit/README.md), она открыла и закрыла AppleSMC без `sudo`; чтения ключей нет. Системная библиотека IOKit доступна через platform bindings Kotlin/Native ([документация](https://kotlinlang.org/docs/native-platform-libs.html)). | Не вводить второй аппаратный код только ради read-only приложения. Для Compose Desktop на JVM всё равно понадобится IPC/JNI; вернуться к кандидатуре для helper в M2, если она упростит проверенное восстановление управления. |
| Swift/AppKit через stdin/stdout Kotlin | [Изолированный значок](../../prototype/menu-bar/README.md) уже показывал показания на `Mac15,7`; интегрированный `status-item-bridge` запущен как дочерний процесс JVM и получает готовые данные. | Сохранить Swift только для нативного элемента строки меню. Один источник коротких снимков в Kotlin, двусторонние команды меню/окна через локальный pipe; реальный путь меню и восстановление после сбоя проверить на устройстве. |

**Текущая интеграция:** Compose/JVM управляет жизненным циклом и опрашивает упакованный C reader. Нативный AppKit-компонент получает тот же снимок и передаёт действия меню в JVM через локальный stdin/stdout pipe. При неожиданной потере дочернего процесса Kotlin показывает окно с ошибкой. Пользователь проверил обновление значка при скрытом окне, оба вида щелчка, читаемость в тесной строке меню и явный выход (M1-03). Пакет должен пройти подпись/нотарификацию в M3. Чтение на проверенной модели не требует `sudo`; будущую запись выполняет только отдельный минимальный helper после проверки прав клиента и возврата системного режима в M2.

## 3. Риски и гипотезы

| Риск / гипотеза | Механизм и проверка |
|---|---|
| **R1. Команда записи принята, а обороты не изменились.** | M2-01: [протокол](../features/manual-fan-control-trial.md) требует перечитать режим и цель, затем наблюдать оба фактических RPM; код возврата IOKit сам по себе не считается успехом. Частичный переход одного вентилятора немедленно запускает восстановление обоих. |
| **R2. Зависание в ручном режиме после аварийного выхода или сна.** | M2-01 требует подготовить независимую команду восстановления раньше writer и ограничивает первую ручную фазу 10 секундами. M2-02 должен добавить внешнего владельца/watchdog, затем испытать штатный выход, crash, сон/пробуждение и обновление. `finally` и signal handler не переживают `SIGKILL`, аварию ядра или потерю питания. |
| **R3. Протокол отличается на Mac mini, Intel/T2 или следующем macOS.** | Поздняя фаза: матрица `модель × macOS × чтение × запись × Auto`; неизвестные комбинации работают только в режиме чтения. Не использовать одно имя ключа или кодировку для всех устройств без проверки типа в runtime. |
| **R4. Нет вентиляторов или температурных датчиков.** | На иных моделях показать состояние «вентиляторы не обнаружены»; для режима от температуры применять только валидный датчик и возвращать системе управление при потере данных. На `Mac15,7` чтение есть, но будущий UI всё равно должен терпеть временную недоступность. |
| **R5. Привилегированный интерфейс принимает команды от чужого процесса.** | M2: проверка подписи вызывающего процесса, allowlist операций, ограничение RPM аппаратными пределами, журнал без паролей и произвольных SMC ключей. |
| **H1. Kotlin/Native достаточно для всего helper.** | M0-03 подтвердил лишь открытие AppleSMC через IOKit. Чтение/запись SMC, ServiceManagement/XPC и восстановление после сбоя не проверены. Проверить в M2-02; если интеграция потребует слишком много обвязки, оставить тонкий Swift helper и Kotlin в UI/общей логике. |
| **H2. Поддержка Mac mini совпадёт с MacBook Pro.** | Проверить на реальном Mac mini после первой версии для `Mac15,7`; наличие в списке совместимости чужого приложения не закрывает эту гипотезу. |

## 4. Следствия для будущего интерфейса

### Возможные операции управления

| Операция | Основание | Статус на нашем Mac |
|---|---|---|
| Вернуть управление системе | Читаются два ключа режима `F0Md`/`F1Md`; открытая [реализация macfan](https://github.com/raminsharifi/MacFanControl/blob/main/src/fan.rs) переключает их. | **Гипотеза:** запись и точная последовательность восстановления не проверены. |
| Установить фиксированные RPM каждому вентилятору | Для обоих читаются отдельные ключи цели `F{n}Tg`, а также `Mn`/`Mx`. | **Гипотеза:** наличие цели и диапазона не доказывает, что macOS примет запись или сохранит заданный режим. |
| «Максимум» | Можно было бы запросить считанный `Mx` для каждого вентилятора. | **Производная гипотеза:** отдельной аппаратной операции «максимум» прототип не обнаружил. |
| Скорость по температуре или кривая | Температуры читаются; приложение теоретически может периодически пересчитывать цель RPM. | **Функция будущего приложения:** готовую аппаратную кривую для этой модели не проверяли; потребуются валидный датчик, цикл управления и возврат системе при ошибке. |

Для M3 Pro сторонние реализации описывают роль `Ftst` при переходе из системного режима: [macfan](https://github.com/raminsharifi/MacFanControl), [исследование macos-smc-fan](https://github.com/agoodkind/macos-smc-fan). Их результат на macOS 26 нельзя объявить нашим результатом на macOS 27. Пока эти действия должны быть скрыты или отключены в UI прототипа мониторинга.

| Можно показать по текущим данным | Пока нельзя обещать |
|---|---|
| Две независимые карточки вентиляторов с текущим RPM и диапазоном, прочитанным из SMC. | Действующие ползунки скорости, «максимум», переключение Auto/Manual и управление каждым вентилятором по отдельности: записи не было. |
| Три выбранных температурных ключа со значениями и сырыми ID в карточках; полный список доступен исследовательской командой reader. | Точное число физических датчиков и безусловные названия «CPU/GPU/SSD» для всех 252 перечисленных ключей. |
| Состояние «0 RPM, система остановила вентилятор» при системном режиме. | Предупреждение о неисправности на основании одного нулевого RPM. |

В Compose окне есть три температурные карточки над двумя вентиляторами. Разделы других температур и диагностики удалены по запросу пользователя; полный перечень ключей сохраняется в исследовательской команде reader. Подписи CPU, GPU и SSD проверены отдельными нагрузочными пробами на `Mac15,7`; сырые ключи остаются видимыми. Действия управления могут появиться только после проверки безопасной записи.

### Требования к окну и строке меню

| Область | Целевое поведение | Ограничение / проверка |
|---|---|---|
| Жизненный цикл | Основное окно можно скрыть и вновь открыть обычным щелчком по единому значку в строке меню macOS; красная кнопка и пункт «Скрыть окно» оставляют мониторинг и значок работающими. Контекстный щелчок двумя пальцами по значку открывает меню с явным действием полного выхода. | При добавлении записи выход должен также инициировать проверенный возврат системного управления (M2). |
| Совмещённый значок | **Один** элемент строки меню одновременно является значком приложения и индикатором: в нём пятисегментная цветная шкала скорости вентиляторов и `TCMz` как температура CPU die max в °C **на `Mac15,7`**. Отдельного статичного значка рядом нет. Общая шкала показывает **максимальный из двух индивидуальных уровней**; так пользователь выбрал способ свести два вентилятора к одному показателю. Конкретные RPM каждого вентилятора и состояние датчика находятся в контекстном меню того же элемента. | При недоступном `TCMz` показывать «— °C»/недоступность, не подписывать другой ключ как CPU. На других моделях потребуется новая карта датчиков. Проверить размер и цвет на живом прототипе. |
| Шкала вентилятора | Для `RPM > 0` уровень каждого вентилятора 1–5 вычисляется **из фактического `F{n}Ac`**, нормализованного по считанным для него `F{n}Mn`/`F{n}Mx`: `1 + floor(5 × clamp((RPM − Mn) / (Mx − Mn), 0, 1))`, результат ограничен сверху 5. В значке заполнены `max(уровень 0, уровень 1)` сегментов; они окрашены последовательно от зелёного к красному, незаполненные нейтральны. Числовые RPM доступны в меню. | `0 RPM` — **0 заполненных делений**, а не уровень 1. При ошибке чтения или некорректном диапазоне — неизвестный уровень, а не 0. При пробе проверить цвет в светлой/тёмной строке меню; системные template-изображения рассчитаны на монохромное содержимое ([Apple: isTemplate](https://developer.apple.com/documentation/appkit/nsimage/istemplate)). |
| Основное окно | Реализовано Compose Desktop окно с `MaterialExpressiveTheme`, карточками и состояниями опроса, подключённое к единому AppKit значку. | Сборка и работа на `Mac15,7` проверены; дизайн-артборды и тесты визуального соответствия появятся после проектирования UI. |
| Автозапуск | Переключатель «Запускать при входе в macOS» на отдельном экране настроек; начально выключен. При включении приложение регистрируется через `SMAppService.mainAppService`; при следующем входе начинает работу в строке меню со скрытым окном. Ручной запуск открывает окно. | Показывать реальное состояние регистрации, в том числе необходимость разрешения в системных настройках. Отказ не превращать в фиктивно включённый переключатель. Оба пути к настройкам проверены в собранном `.app`. |

**Целевые сценарии приёмки.** Скрытие окна не прекращает обновление шкалы и температуры в совмещённом значке. Обычный щелчок по значку переключает видимость окна; контекстный щелчок двумя пальцами открывает меню с RPM обоих вентиляторов, действиями открытия окна, настроек и выхода. Шестерёнка в окне тоже открывает настройки. При фактических 0 RPM обоих вентиляторов шкала пуста; когда они вращаются с разными относительными скоростями, значок показывает **больший** уровень, рассчитанный по диапазону **своего** вентилятора. Если `TCMz` пропал или невалиден, значок показывает недоступность температуры, а не подменяет её другим ключом. После включения автозапуска и разрешения macOS значок появляется в строке меню при следующем входе; после выключения приложение не запускается автоматически.
